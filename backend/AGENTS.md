# Backend AGENTS.md

루트 [AGENTS.md](../AGENTS.md)의 공통 규칙을 전제로, `backend/**` 작업에 적용한다.
프론트엔드·워치·AI·인프라에는 이 절차와 템플릿을 자동 적용하지 않는다.
아래 코드 경로는 저장소 루트 기준이다.

## 1. 기준 문서

- 요구사항: `docs/design/requirements.md`, `docs/design/mvp.md`
- API 계약: `docs/design/api/`, 논리 스키마: `docs/design/erd.md`, 물리 스키마: `docs/design/schema.sql`
  - 구현은 계약을 따른다. 계약과 다르게 구현해야 하면 임의로 진행하지 않고
    합의 후 문서를 먼저 수정한다. API 초안을 확정 계약으로 취급하지 않는다.
  - 명세에 없는 API, Entity, 필드를 임의로 추가하지 않는다.
- 코드 규칙과 담당 도메인: 현재 Jira와 팀에서 확정한 백엔드 규칙·소유권을 확인한다.
  - 전용 컨벤션·역할 분담 문서는 아직 없다. 미확정 규칙을 추정하지 않는다.
  - 컨벤션 예외는 구현 전에 이유와 대안을 제시한다. 다른 담당자 소유 도메인과 공통 설정을 임의로 수정하지 않는다.
- 아키텍처 결정: `docs/adr/`
- 실행·빌드 명령은 프로젝트 초기 구성 시 `backend/README.md`에 확정한다.

## 2. 검증

현재 백엔드는 Java·Spring 채택만 확정되어 있고 실행 코드, 빌드 도구와 `backend/README.md`는 없다.
Java 버전·Gradle·Spotless 등의 도입이나 명령을 추정하지 않는다. 초기 구성에서 실제 실행 가능한
테스트·정적 검사·빌드 명령을 README에 기록하고 이후 완료 검증에 모두 적용한다.
그 전에는 플랜에서 실행 가능한 검증 명령·대체 검증과 통과 조건을 정한다.

작은 코드 변경도 관련 테스트 통과는 필수다. 문서 등 실행 코드가 없는 변경은 링크·내용 정합성 등
사전에 정한 대체 검증을 수행한다. 테스트 코드만 바꾸어도 해당 테스트를 실행한다.
필수 검증을 영향도 판단으로 임의 제외하거나 기대값을 약화해 통과시키지 않는다.
완료 검증에서 작업 범위 밖의 파일을 수정하지 않는다.

결과는 통과·실패·미실행·해당 없음으로 구분하고 명령·대상 상태·근거를 남긴다.
필수 검증의 실패·미실행은 완료가 아니다. 환경 부족은 미실행으로 보고한다.
검증 후 코드를 바꾸면 영향받는 검증을 다시 실행한다.

## 3. 적용 범위

변경이 닿는 범위에 따라 세 단계 중 하나를 적용한다. 섞이면 가장 높은 단계를 따른다.
판정과 근거는 플랜 파일 첫머리에 적는다. 문서 변경이어도 아래 트리거에 해당하면 게이트를 우선한다.

| 단계 | 조건 | 적용 |
| --- | --- | --- |
| 검증만 | 문서, 주석, 테스트 코드만 변경 | 2장 검증 |
| 기본 | 아래 트리거에 해당하지 않음 | 4장의 플랜·구현 완료 기준과 RunWay 리뷰 기준 적용 |
| 게이트 | 아래 트리거 중 하나 이상 | 4장의 완료 기준에 더해 사람의 플랜 승인과 높은 위험 독립 리뷰 |

트리거. diff 또는 플랜에 하나라도 있으면 해당한다.

- `docs/design/api/`, `docs/design/erd.md`, `docs/design/schema.sql` 변경 또는 그 계약과 다른 구현
- DB 마이그레이션, 공통 모듈·보안 설정, 다른 담당자 소유 도메인
- `@Transactional` 경계의 신설·변경, 한 유스케이스에서 둘 이상의 Repository 쓰기
- 인증·인가 코드, 토큰·쿠키, 건강·GPS 개인정보 접근
- 러닝 기록 유실·중복, 동시성, 업로드 재시도·순서 보장에 영향을 주는 변경
- 메시지 발행·소비와 캐시 키·TTL(해당 기술이 도입된 경우)
- 빌드·의존성·실행·배포 설정, `.env.example`

## 4. 작업 절차와 게이트

기본·게이트 단계에서 AI는 플랜, 구현, 리뷰의 완료 기준을 충족한다.
리뷰 산출물 생략 여부는 아래 RunWay 리뷰 편성을 따른다. 산출물은 다음
단계가 Jira 요구사항, 정본 문서, 저장소 상태와 함께 작업을 재현할 수 있을 정도로 작성한다.
동일 worktree를 여러 작업자가 동시에 수정하지 않는다.
작업 재개·인계 시 브랜치·기준 커밋·diff·플랜·검증 상태를 다시 확인한다.

1. **플랜** — 루트 `plans/<Jira-Key>.md`(5장). 설계, 미확정 항목, 기준선(시작 시점의 미커밋 변경 목록),
   3장 판정과 트리거, 열리는 리뷰 게이트, 인수 테스트 목록(동작마다 테스트 이름, 전제·입력,
   기대 결과인 응답·오류 코드·상태 변화. 테스트로 확인할 수 없는 변경은 대체 검증과 통과 조건).
   이후 단계는 기준선의 기존 변경을 보호한다. 완료 기준: 모든 동작에 테스트 또는 대체 검증이
   대응하고, 계약·스키마·공용 파일 영향이 팀과 합의되어 있다.
2. **구현** — 완료 기준: 플랜의 인수 테스트가 모두 존재하고 통과하며 2장의 필수 완료 검증이
   성공한다. 플랜 목록 대비 테스트의 추가·삭제·기대값 변경과 플랜 이탈은 사람 확인 후
   플랜에 기록되어 있다. 테스트 실패를 숨기거나 검증 범위를 임의로 약화하지 않는다.
3. **리뷰** — 루트 `plans/<Jira-Key>-review.md`. 변경 단위마다 diff와 그 단위가 참조하는
   계약 절만 읽고 관점을 한 번에 적용한다. 관점별로 기준 문서를 다시 읽지 않는다.
   Secret 점검은 diff 전체에 한 번, 단위 간 정합성은 마지막에 한 번(계약·트랜잭션
   경계·오류 코드)만 본다.
   - 계약 정합성 · 정확성(경계 조건, 실패 경로) · 보안(입력 검증, Secret)
   - 테스트 실효성: 플랜 목록과 실제 테스트의 대조, 기대값 변경 기록의 타당성
   - 조건부: 트랜잭션·인증 트리거에 해당하는 단위에만 동시성·트랜잭션 경계와 인가.
     게이트 개폐와 근거를 적는다.
   측정 칸: 읽은 기준 문서 절 수, 열린 게이트, MR 리뷰에서 뒤늦게 발견된 누락(병합 후).

리뷰 편성은 RunWay의 변경 영향에 따른다. 작은 변경도 기본 단계의 플랜 파일과 테스트는 생략하지 않는다.

- **작은 변경**: 요구와 수정 위치가 명확하고 영향이 국소적이며 게이트 트리거가 없다.
  자체 점검으로 플랜과 실제 결과를 대조한다. 독립 리뷰와 리뷰 파일은 생략할 수 있다.
- **일반 기능**: 작은 변경에 해당하지 않는 기본 단계. 구현과 분리된 리뷰어 한 명이
  최종 독립 리뷰 1회에서 해당 관점을 모두 적용한다.
- **높은 위험**: 게이트 단계. 독립 리뷰어 한 명이 정상 관점과 전제를 깨는 입력·교차 실행·실패 경로를
  함께 검토한다. 구체적인 요청·동시 실행 시나리오와 증거·한계를 남기고, 결함이 없더라도 시도한 사례를 적는다.
  A/B 두 리뷰와 합집합 절차는 요구하지 않는다.

공통 관점에 더해 관련 변경에만 다음 관점을 적용한다.

| 변경 기능 | 조건부 리뷰 관점 |
| --- | --- |
| 인증·건강/GPS 접근 | 소유자·동의·권한 철회, 우회 요청, 정보 노출 |
| 러닝 상태·저장·업로드 | 중복·순서 역전·동시 실행, 트랜잭션·재시도·복구 |
| 모바일·워치 연동 API | 연결 단절 시 서버 처리, 권한·단위·시간 정합성 |
| 추론·외부 API | 누락·잘못된 입력, 타임아웃·오류 전파, 계약 불일치 |
| 백엔드·공통 설정 | 적용 범위, 기동 실패·복구, 비밀정보 취급 |

- **플랜 승인**: 게이트 단계는 플랜 완료 후 사람이 확인하고 승인·수정 지시를 플랜에 추기한 뒤 구현한다.
  이미 승인된 내용은 반복 확인하지 않는다.
- **분리 리뷰**: 필요한 독립 리뷰는 구현과 다른 세션 또는 사람이 플랜·diff·정본 문서와 검증 결과를 보고 수행한다.
  구현자의 재독을 독립 리뷰로 기록하지 않는다. 리뷰어는 코드를 수정하지 않는다.
- **리뷰 완료**: 필수 지적은 수정·재테스트 후 해당 부분과 영향 범위를 재검토한다. 일반 기능에도 적용한다.
  새 영향이 없으면 전체 리뷰를 반복하지 않는다. 필요한 리뷰를 수행하지 못하면 미실행으로 보고한다.
  팀원에게 메시지를 보내는 것은 사용자 요청이 있을 때만 한다.

게이트 단계 MR 5건 연속으로 사후 누락이 0이면 리뷰 기준 완화를, 기본 단계 MR에서 사후 누락이
나오면 트리거 확대를 검토한다. 측정 결과 없이 정책을 자동 변경하지 않는다.

## 5. 플랜과 기록

- 플랜과 리뷰 파일은 **저장소 루트의 `plans/`** 에 둔다. 이 문서가 `plans/`로만 적은 곳도
  모두 루트를 가리킨다. `.gitignore`의 무시 규칙이 루트에 고정된 `/plans/`와 하위 디렉터리의
  `/*/plans/`뿐이므로, 그 밖의 위치에 두면 커밋하지 않기로 한 기록이 커밋 대상이 된다.
- worktree에서 작업했으면 완료 후 산출물을 기본 체크아웃의 루트 `plans/`로 옮긴다.
  worktree를 정리하면 그 안에만 있던 플랜과 리뷰 기록이 함께 사라진다.
- 플랜과 리뷰 결과는 커밋하지 않는다. MR 본문에 플랜 요약, 플랜 대비 변경점과
  리뷰 결과 요약을 남긴다.
- 플랜과 리뷰 파일은 [플랜 양식](templates/plan.md)과 [리뷰 양식](templates/review.md)으로
  작성하고 측정 칸을 비워 두지 않는다.
- 리뷰 파일의 측정 칸과 플랜의 인수 테스트 목록은 MR 본문 "테스트" 절에 옮겨 적는다.
- 플랜에서 프로젝트 수준 결정이 나오면 `docs/adr/`로 승격한다.
- 미래 작업에 필요한 사실을 플랜이나 MR 본문에만 남기지 않는다. 계약, 스키마와
  코드 규칙 변경은 반드시 정본 문서(`docs/design/api/`, `docs/design/erd.md`, `docs/design/schema.sql`,
  확정된 백엔드 규칙과 `docs/adr/`)에 반영한다.

- 아직 관찰할 수 없는 측정값은 사유와 함께 미확인으로 적는다. 작은 변경의 리뷰 생략도 MR에 명시한다.
- worktree를 사용하면 해당 Jira의 작업 디렉터리에서 수행한다. 기록 보존 시 기존 동명 파일을 덮어쓰지 않는다.
